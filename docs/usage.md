# Using Warden

On a fresh installation, Warden opens its interactive guide. Eight optional chapters cover the menu, connections, approval practice, notifications, context and quotas, history, train-guard, power, phone access, and customization. The guide uses live app state, saves progress, and can be reopened from **Interactive Guide…** in the menu or Setup. Practice approvals never execute a command. Start a coding session, connect Claude Code's hooks if needed, and choose whether to allow notifications and open at login. Existing installations keep their login setting and saved alert choices. The default alert style is a notification with the system sound; voice lines are optional in General. Settings also control quiet hours and quota warnings. Voice lines and alert sounds stay silent while a microphone is in use, as during a call; Warden reads only whether a microphone is in use, which needs no permission.

## Setup and permissions

**Settings → Setup** shows the macOS notification permission, whether banners are allowed, login-item registration and pending approval, the optional power service, and local source coverage. It offers a notification test and links to the relevant settings. Checking these states never requests a new permission. A submitted test does not prove macOS displayed it: Focus and alert style still apply.

Ordinary monitoring and idle Keep Awake need no administrator password. Closed-lid work requires the optional signed power service and administrator approval in macOS. Registration, approval and active protection are separate states. Power settings can retry registration when it has been removed. If the service stops confirming protection, Warden stops showing it as active; removing an unresponsive service waits for confirmation that normal sleep has been restored and reports a timeout instead of waiting indefinitely.

Keep Awake covers active coding sessions, running train-guard jobs, and answerable prompts awaiting a paired phone. When these no longer need protection, normal sleep resumes. Battery reserve, power-source preferences and thermal safeguards still apply. Validate the privileged closed-lid path with a disposable job and restoration of normal sleep on the target hardware.

## The menu

The lantern in the menu bar opens a standard macOS menu, laid out like the system Battery and Weather menus. The number beside it counts sessions that are working or waiting for you. The lantern is lit while agents work, turns solid with an exclamation mark when a session needs you, and dims while alerts are snoozed. A setting can add a usage percentage: the fullest limit or one you choose, used or remaining.

Each session is listed by its title, with the agent and folder below. Titles come from Claude Code's generated title or session name and from Codex thread names. A Claude session without one, such as a run started through the SDK, is named after the start of its last prompt, which Warden keeps in memory only. A session with no title at all shows its folder.

- **Needs You** lists approvals first, then questions, errors, and interrupted turns, oldest first. A run that a program started, such as `claude -p` or `codex exec`, ends with its turn, so it stays here only while its process runs; one that stopped on an error moves to Recent Sessions and says why. Questions include the ones Claude asks with its question prompt and Codex with its input tool, which hold the turn until you answer. The subtitle shows what a tool would do, such as its command or file, quotes the question, or says what stopped the session, such as a usage limit or an expired login. Under a Claude Code or Codex prompt, **Allow**, **Allow for This Session**, **Always Allow**, and **Deny** answer it, when the agent offers them, and a question's options pick an answer; see [Answering prompts](#answering-prompts). A turn stopped with Esc or a declined tool waits here while its agent is still open, because the agent then asks what to do instead. It alerts you only if it still waits 30 seconds later, since Esc usually comes right before you redirect the agent. Click a session to bring its window forward. Hold Option to mute alerts for it. Under a Claude session with a large context, **Reply within 22 min to keep its cache** says how long its prompt cache lasts and what a later reply costs; see [Prompt cache](#prompt-cache). Under a session that stopped on an error that may be the provider's, such as an overloaded service, the provider's status page can name the incident, when **Check the provider's status page when a session fails** is on in Settings.
- **Working** shows each running session with a ring for its context window and how long the current turn has run. A session whose own turn ended while its subagents, such as Claude background agents or Codex spawned threads, still work stays here with their count. A Claude session that hit a usage limit and waits for the reset to continue by itself shows an hourglass and the time it resumes; if the reset comes while the Mac sleeps, Claude Code waits for Enter instead, and the session moves to Needs You. A session whose log has not changed for ten minutes says **No new output**: a long tool run, a long reasoning step, or a stalled request, which Esc in its terminal stops. A session whose request Claude Code retries after an error says so, such as **Offline, retrying (3 of 10)**.
- **Usage** shows each limit window with a tick where usage would sit at an even pace, and the time until it resets. After its reported reset, a window shows as reset until a new reading arrives, for up to six hours; the reading that follows can confirm that quota is available again, and the alert names the sessions the limit stopped. Banked Codex limit resets show when the next one expires. Limits on one model appear on their own row, such as Claude's weekly Fable limit or Codex's Spark limits, since they can run out while the plan still has room, and so does Claude's extra usage when it is on. When the average pace would exhaust a window before its reset, Warden says when, marked as an estimate. The section's tooltip adds each limit's recent pace, from the readings of the last hour.
- **Work Planner** checks a 30, 60, or 120 minute work session against the shared and model-specific limits of each account. It uses recent changes in reported quota, shows the first projected constraint, and lets you inspect each reading and pace estimate. **Before you step away** expands to show decisions waiting for you, high context, large quiet caches expiring within the selected duration, reported auto-resumes, and missing current shared quotas for working accounts. Power status distinguishes idle sleep prevention from confirmed closed-lid protection. Each session check includes its source and observation time. Old scans require refresh. This is a review of observed constraints, not a guarantee that an unattended task will finish. It needs at least three readings over ten minutes with a measurable change, learns again after a reset or long gap, and makes no prediction beyond a reset. It never starts work or switches accounts.
- In the planner, compare **half, recent, or twice the recent pace**, and choose to **keep 10% or 20% unused**. Warden distinguishes reaching your margin from reaching a provider limit, and charts the observations behind each estimate. This is a scenario, not an enforced reservation or a promise about the next task.
- **History** opens a native window with three reports. Its menu item says what today cost in a plan's own currency, such as `Today: Claude 7d +7% · Codex 7d +33%`.
  - **Usage**: 7, 30, and 90 day periods, an account filter, daily tokens or requests, project and model rankings, and a CSV export of the selected data. Tokens are the default, including models without known API prices. **Settings → Usage** can pause history or enable **API price equivalents**: optional comparisons at standard public API prices, never subscription charges or an invoice. Unknown prices remain unavailable, and partial amounts say what they exclude. History starts with logs changed in the last five weeks and retains collected totals for 90 days; empty days may have no available records. Filter by **project**, then select a day to inspect its input, cache writes, cache reads and output; rankings and CSV export follow that selection. The cache percentage uses recorded input only and does not measure subscription savings.
  - **Limits**: where each 5-hour, weekly, and model limit went. With your plan's monthly price entered in **Settings → Usage**, each weekly limit also reads in the money you pay for it: a point stands for a hundredth of a week's share of the price, so the report shows what each project's share cost and how much of the week's value is still unused, and the menu's History line adds today's share. The 5-hour and model limits pace use within the week and have no price of their own. Each time Claude Code or Codex reports a higher percentage, Warden splits the rise among the sessions that used tokens since the previous rise, in proportion to the API list price of their use, which stands in for how providers meter plans. A rise with no local use counts as **No local use**: the web, the phone, or another computer. The report shows the current window by project, points per day, and past windows. With API price equivalents on, it also says what one point of the limit is worth at API prices, and so the whole window, and whether this window drains faster than past ones for the same use. **What a point buys** compares each window with the median of past ones, so a limit that fills faster for the same use, as when a provider tightens it, stands out; the provider may also have changed nothing and the use differed. These are estimates; providers report only the account's total. Session tooltips give each session's share of the current windows.
  - **Activity**: a timeline of the day in which each session works, waits for you, or waits for a limit to reset, with how long agents waited and for what, the median time you took to answer, how many answers came from Warden, and the share of agent time spent working. The last seven days compare work and waiting. **Settings → Usage** can turn recording off.
- **Recent Sessions** holds finished, paused, and ended sessions. A Claude session with a large context shows how long its prompt cache still lasts, such as **Cache 41 min**, and **Cache expired** after that.
- **Ignore train-guard** appears once [train-guard](https://github.com/fus3r/train-guard) is installed. train-guard supervises an agent's long jobs: it pauses a job while the Mac runs on battery and lowers its priority while the battery is warm, without restarting it. Check a session to let the jobs its agent starts under train-guard run at full speed, on battery too, and uncheck it to put them back under train-guard's policy; train-guard applies either at its next check. It learns which agent started a job from the session id that Claude Code and Codex give the commands they run, which train-guard 0.5 and later record for a job started with `train-guard run`; a job it attaches to later gets an agent only when `--agent` names one. Under each session, the menu names its guarded jobs and what train-guard does with each now: paused, at low priority, or at full speed. **Settings → General → Long Jobs** manages the integration; see [train-guard](#train-guard) for installation details.
- **While You Were Away** appears at the top for half an hour after you come back from 15 minutes or more away from the Mac, with no keyboard or mouse input or with the screen locked. It says which sessions finished or wait for you, how long agents worked and waited, and how each limit moved or reset, and a silent notification says the same. Its submenu opens the session that has waited longest. Warden keeps only the start of the absence, in memory.
- **Alerts** switches between all alerts, only sessions that need you, or a one hour snooze. **Alerts by Session** gives one session its own style, such as voice only for a long task or no alerts for a side experiment. A session keeps its agent's style from Settings until you pick another.

The menu's limits, recent sessions, and alert choices can each be hidden in Settings.

### Prompt cache

Claude keeps a session's context in its prompt cache for an hour after the request that last used it with a subscription, or five minutes with an API key. A reply within that time reads the context from the cache at a tenth of the input price; a reply after it writes the whole context to the cache again, at twice the input price for an hour-long cache. With the large contexts of long sessions, that difference is several points of the 5-hour limit. For a Claude session that waits for you, Warden shows how long the cache lasts and what a later reply would cost, in points of the 5-hour limit at the current window's rate from the [Limits report](#the-menu), or in tokens before that rate is known. Five minutes before an hour-long cache expires, an alert reminds you, when the cost is a point or more. With Claude Code connected, the expiry and the tokens come from Claude Code's own status line report (2.1.251 and later), which also gives the session's cache hit ratio and the likely cause of its last miss, such as changed tools; otherwise they come from the last cache write in the session's log. The cost is an estimate; providers do not report what one request takes of a limit.

Clicking a session returns to its live terminal or host app. Warden identifies the process from the bridge or the session's open transcript, so two conversations in the same folder are not confused. Terminal and iTerm select the session's own tab. With the [VS Code companion](https://github.com/fus3r/warden/tree/main/Extensions/warden-terminal), VS Code selects the exact terminal and window, including terminals in editor tabs or in a window for another project. Install it with `./Scripts/install-editor-extension.sh`; without it, Warden activates the live host app. If the session no longer has a live host, Warden opens Terminal with `claude --resume <session-id>` or `codex resume <session-id>`, in the session's folder and account. Claude background sessions use `claude attach`. The click never opens Finder or sends a new prompt. macOS asks once before Warden may control Terminal or iTerm. If opening Terminal fails, Warden offers to copy the resume command. Once permitted, Warden also stays quiet about a session whose Terminal or iTerm tab is in front; Settings can turn this off.

Settings can add global shortcuts, off by default: one opens the menu, and one brings forward the session that has waited longest for an answer. They use the system's hot key service and need no Accessibility permission.

## Automations

Warden can run your own scripts on its alerts, for anything it should do beyond a notification: send the alert to your phone, start a job when quota comes back, or keep a log. Turn on **Run scripts on alerts** in **Settings → Automations**, then put executable files in `~/Library/Application Support/Warden/Automations`. On each alert, every script runs once, in the background, for at most 30 seconds, with the event as JSON on its standard input and in `WARDEN_EVENT`, `WARDEN_TITLE`, `WARDEN_MESSAGE`, `WARDEN_AGENT`, `WARDEN_PROJECT`, and `WARDEN_SESSION`:

```json
{"event":"needs-you","at":"2026-09-26T12:24:23Z","title":"Claude · api: Migrate billing tables",
 "message":"Waiting for approval to use Bash","agent":"Claude","project":"/Users/me/api",
 "session":"5c1f…","alerted":false}
```

Events are `needs-you`, `finished`, `context`, `cache-expiring`, `limit-warning`, `limit-reached`, `limit-unused`, `quota-available`, `away-summary`, and `test`. Scripts get every alert that the alert settings turn on, even while alerts are snoozed, in quiet hours, or limited to Only When Needed, with `alerted` saying whether Warden also showed it; a muted session sends nothing. **Add Phone Example** writes `notify-phone.sh`, which sends alerts to the [ntfy](https://ntfy.sh) app once you write a topic in it, and **Send Test Event** runs every script once. Once a phone is paired for [Warden on your phone](#on-your-phone), scripts also get the page's address in `WARDEN_PHONE_URL`, and tapping the example's notification opens it. The encrypted phone service also sends generic push notices when enabled; automation scripts can send their own content. An alert's title and text can quote an agent's question, but for a prompt they name only the tool, never its command or file.

## train-guard

[train-guard](https://github.com/fus3r/train-guard) supervises a long-running job: it pauses the job while the Mac runs on battery and lowers its priority while the battery pack is warm, then lets it continue, without restarting it. Warden works with it in two ways.

Only jobs launched with `train-guard run` or explicitly attached are controlled. Agent instructions request that behavior; they do not intercept other jobs. Lower priority is a scheduling hint, not a power cap or a measured battery-life improvement. Use application checkpoints for recovery after reboot; suspension does not preserve RAM across a restart.

- **Settings → General → Long Jobs** installs train-guard `0.5.0.dev0` and its self-contained runtime from the signed app. No Python installation or dependency download is needed. Warden verifies every payload file against a SHA-256 manifest before making changes. Each installation uses a separate folder in `~/.local/share/train-guard`, with a command link in `~/.local/bin`; an update switches the link only after the new command and policy validate. Running guards block replacement or removal. Existing Python-based managed installs offer an update to the autonomous runtime, even at the same train-guard version.
- **Migrate…** upgrades the earlier shell installation when its known command occupies that link and no legacy guard is active. The script, logs, persisted jobs and launch agent stay in place. Its literal policy values are translated only when no Python policy exists (`ecore` becomes `gentle`), and its override list is copied if absent. Legacy persisted jobs continue to belong to the old script; use its full path to manage them. Unrelated commands and unmanaged install folders are left untouched. Removing the managed package restores the legacy command.
- The same place adds a short section to each account's `CLAUDE.md` and Codex `AGENTS.md` that tells agents to run long or heavy jobs under train-guard. A file that already mentions train-guard, in your own words, stays as it is, and so does one that is not readable text. A symbolic link, as to a dotfiles folder, stays a link, and its target gets the section. Each file is saved once as `CLAUDE.warden-backup.md` or `AGENTS.warden-backup.md` before the first change, and the section is marked so that **Remove** takes out exactly what Warden added.
- **Remove…** deletes what Warden installed, the link, and its sections, after checking that no guard still runs, and train-guard's login agent when it would start Warden's copy. The jobs' state and logs in `~/.train-guard` stay.
- The menu's **Ignore train-guard** lets a chosen agent's jobs bypass it, as described in [The menu](#the-menu). A train-guard installed another way, such as with pipx or the earlier shell script, works the same once it records agents.

## Answering prompts

With Claude Code connected, its `PermissionRequest` hook shows each prompt in Warden while the terminal shows it too. Claude Code takes the first answer, from either place. **Allow for This Session** applies the rule Claude Code suggests to this session only and never writes it to a settings file. **Always Allow**, offered when Claude Code suggests a rule to keep, answers as the terminal's "Yes, and don't ask again" does: Claude Code keeps that exact rule where it says, usually the project's `.claude/settings.local.json`, and its tooltip names the rule and the file. Warden writes no settings file itself. **Deny** stops the turn, as No does in the terminal. For a question with a single choice, each option answers it. Warden never answers on its own: when you answer in the terminal, or no one answers before the hook's ten minutes run out, Warden releases the prompt and withdraws its notification. Without Warden running, the hook returns at once and the terminal decides alone.

The bridge sends the prompt to Warden through a socket in a folder only your user can open, and Warden checks that the caller is your user. The tool's command or file stays in Warden's memory and is never written to disk. Settings can turn answering off.

Codex 0.157 and later runs the threads of the `codex` terminal app in a shared background server, `codex app-server`, which tells every client when a thread waits for approval or an answer. Codex's session logs never record that wait, so without this Warden would show the session as working. While answering is on, Warden connects to that server through its socket in the account folder, `~/.codex/app-server-control`, which only your user can open, and puts the session under Needs You with the command, the files of an edit, or the question. The server sends the prompt to the terminal and to Warden and takes the first answer, and the terminal withdraws its prompt when Warden answers. **Allow** runs the command or applies the edit; **Allow for This Session** is offered when Codex offers it, such as "don't ask again for these files"; **Always Allow commands starting with …** answers as the terminal's "Yes, and don't ask again for commands that start with …" does: Codex adds that prefix rule to `~/.codex/rules/default.rules`, and the tooltip says so. **Deny** stops the turn, as "No, and tell Codex what to do differently" does. A Plan-mode question takes one of its options. Warden answers only commands, edits, and questions, and leaves every other request, such as MCP forms and permission requests, to the terminal.

This needs approvals on in Codex, such as `approval_policy = "on-request"` with `sandbox_mode = "workspace-write"` in `~/.codex/config.toml`, or `codex -a on-request -s workspace-write` for one session; with `approval_policy = "never"`, Codex never asks. A `codex` session started with `-c`, `--profile`, `--no-daemon`, or `--oss` runs its own server, and so do the VS Code extension and the ChatGPT app, so their prompts stay in their own window. `codex exec` never asks. Warden reads the version the server reports and connects only to 0.157 or later, and joins a thread only while it waits.

## Sources

For full Claude Code coverage, choose **Connect Claude Code** in the menu or in Settings. Warden adds a status line and lifecycle hooks to `~/.claude/settings.json` and leaves unrelated settings intact. It saves the original file once as `~/.claude/settings.warden-backup.json` and the state before each change as `settings.warden-previous.json`. If you already use a custom status line, Warden keeps it: the bridge runs your command with the same input and prints its output. **Disconnect** removes the hooks and restores that status line. If the app moves, the menu offers to repair the connection.

Connecting shows exactly what changes in the settings file before anything is written. Warden adds only the hook events the installed Claude Code knows, read from its version, because Claude Code skips a whole settings file that names an event it does not know. After an update brings a new event, the menu offers to repair the connection. Cursor and Devin also run the hooks in Claude Code's settings; the bridge ignores their sessions.

The bridge records context and limit percentages, event types, the session title, and where the session runs (process ID, terminal device, host app). It does not store prompts or replies; for an approval it keeps only the tool name, and for a failure only the error type.

Claude limits stay current without a running session. Every ten minutes and when the menu opens, Warden starts Claude Code in print mode and sends only the `get_usage` control request, the data behind `/usage`. No prompt is sent, so no model request is made. Safe mode keeps hooks, MCP servers, and plugins off, and the session is not saved. Claude Code answers with its own sign-in, which contacts Anthropic. Warden never reads Claude credentials. Claude Code marks this request experimental, so Warden reads only the documented fields: the 5-hour and 7-day windows, limits on one model (`model_scoped`, and the older `seven_day_opus` and `seven_day_sonnet`), and extra usage when it is on. It keeps the status line values when a read fails. Settings can turn this off.

Since Claude Code 2.1.234, a session stopped by a usage limit continues by itself when the limit resets. Its Notification hook says when it did, and when it will not: the reset came during a long sleep and Claude Code waits for Enter, or continuing is turned off. Warden moves such a session back to Working or to Needs You.

While a Claude process runs, Warden also reads `claude agents --json`, the list Claude Code documents for status bars, once a minute and when the menu opens. It adds waits that hooks and transcripts do not show, such as a sandbox request or an open dialog, the process of each live session, and background sessions that are blocked on you.

Codex needs no configuration for monitoring. Warden reads the recent ends of session logs under `$CODEX_HOME/sessions` or `~/.codex/sessions`, and thread names from `session_index.jsonl`. It does not replace Codex's existing `notify` command. Codex context is an **estimate** from last input tokens and the logged context capacity. Threads Codex spawns, and its reviews, have logs of their own; Warden counts them with the session that started them instead of listing them. Limits are kept per bucket, so a turn on a model with its own limits, such as GPT-5.3-Codex-Spark, does not replace the plan's windows. To keep Codex limits current between sessions, Warden asks the local Codex CLI every ten minutes and when the menu opens, through the read-only `account/rateLimits/read` request of `codex app-server`. Codex answers with its own sign-in, as its `/status` command does, which contacts OpenAI. Warden never reads Codex credentials. The same answer names the plan, any credits, and limit resets the account has banked, which the Usage section lists; Warden never spends them. Settings can turn this off.

### Several accounts

Warden follows every account folder it finds beside the defaults, such as `~/.claude-work` or `~/.codex-personal`, when it holds session logs, and any folder added in Settings, such as one that `CLAUDE_CONFIG_DIR` or `CODEX_HOME` names elsewhere. Each account keeps its own sessions, limits, history, and, for Claude Code, its own connection in its own `settings.json`. Another account's limits start with its name, such as "work 5h".

### Scripts and status bars

`WardenBridge status` prints one line, such as `1 needs you · 2 working · Claude 5h 87% · Fable 7d 94%`, and `WardenBridge status --json` the same as JSON. The bridge is at `Warden.app/Contents/Helpers/WardenBridge`. It reads only counts and limits; session titles and folders stay in the app.

## On your phone

Builds configured with the hosted relay offer **Settings → Phone → Anywhere**, which pairs a phone through an expiring QR code. It works across Wi-Fi and mobile networks, without a VPN or certificate profile. The Mac and phone encrypt session state and replies with per-device keys; the relay forwards opaque packets. The consumed QR is revoked and exchanged for a new device credential. Web Push sends a generic notice, without a command or question. On iPhone, add the page to the Home Screen and enable notifications there. Deployment, privacy boundaries and verification are described in [Relay/README.md](https://github.com/fus3r/warden/tree/main/Relay). Builds without a relay use local-network access directly.

**Local network** mode lets a phone on the same Wi-Fi or Ethernet network open Warden in its browser: what needs you, with the command or question and the same answers as the menu, the sessions at work, and your limits. An answer from the phone is the same as one from the menu, and the terminal keeps its prompt. Nothing goes through a server: the phone talks to this Mac directly, over HTTPS.

Setting it up takes a few minutes, once:

1. Turn on **Answer from your phone**, then choose **Send with AirDrop…** or **Save Profile…** to give the phone Warden's profile. On an iPhone, install it in Settings → Profile Downloaded, then turn on **Warden on** your Mac in Settings → General → About → Certificate Trust Settings. The fingerprint iOS shows under the profile's More Details matches the one in Warden's settings.
2. Choose **Pair a Phone…** and scan the code with the phone's camera. Safari opens Warden and pairs. To open it like an app, add it to the Home Screen from the Share menu, and pair it there with the six digits shown under the code, since a Home Screen app keeps its own cookies.

The profile holds a root certificate Warden makes for this Mac. It can vouch only for this Mac's local name, such as `ada-macbook-pro.local`, and Warden discards its private key as soon as it has signed Warden's server certificate, so it can never sign anything else. That certificate lasts 825 days, the most Apple accepts. **Make New…** issues new ones, which each phone then installs again; a new local name for the Mac, in Sharing settings, needs that too.

A pairing lasts five minutes, works once, and closes after five wrong tries. The phone then keeps a random secret in a cookie only Warden's page can use, and Warden keeps a hash of it. An answer also needs the page's own origin and header, so another website cannot answer through the phone's browser. In local-network mode, Warden listens only while the companion is on and a phone is paired or a pairing is open, only on Wi-Fi or Ethernet, never over a VPN, and refuses devices outside the local network. **Unpair**, in Settings or on the phone, forgets a phone.

The page follows changes while open. Remote mode includes generic Web Push notifications after the phone grants permission. Local-network mode can use the optional example in [Automations](#automations) for separate phone alerts.

## Widgets

Warden's widget, in three sizes, shows what needs you, how many agents work, and the fullest limits with their even-pace tick and reset, on the desktop or in Notification Center: right-click the desktop, choose Edit Widgets, and search for Warden. Clicking a session in it brings that session forward; clicking elsewhere opens the menu. The widget runs in a sandbox that may read only `~/Library/Application Support/Warden/Widget`, where Warden writes what it shows: folder names, agents, states, tool names, and limits, never a title, command, or question. Warden refreshes it when that changes and every quarter hour, and the widget dims when Warden has not written for half an hour.

Warden labels unavailable information instead of fabricating it. A completed answer ending in a question mark is a heuristic, so it can miss questions or flag rhetorical ones. When a limit read fails, the menu says when the value was last reported. Values older than 30 minutes do not drive forecasts or the menu bar percentage. A reset time that passed is shown as pending until a new provider reading arrives. The app does not inspect screen contents, browser tabs, API keys, or account cookies.

## Data and limits

- Session scan every eight seconds. At most 28 recent Claude logs and 56 Codex logs are considered, since Codex keeps spawned threads in logs of their own; Warden reads the first 64 KB and a bounded tail of 1 MB (Codex) or 512 KB (Claude). It expands a recent unresolved Codex tail to at most 8 MB. Unchanged files use an in-memory cache. Claude subagent transcripts are read only to see whether they still work.
- Usage history reads each log only once. The first read covers logs changed in the last five weeks, a few seconds for gigabytes of logs; later reads, once a minute and when the menu opens, take only the lines a log gained. Warden keeps no text, only token counts per day, agent, model, and project folder, for 90 days, including logs a provider has since deleted. Logs still being written keep a read position in `usage-active.json`, saved at most every five minutes; a log left alone for three days moves to `usage-archive.json`. A parsing checkpoint preserves model and cumulative counters when it resumes, so earlier usage is not counted again. Older archives recover that checkpoint once, only if the corresponding log resumes.
- A session counts as running while its agent process lives: the exact process from the bridge, or the most recent session per folder for each agent process there. A quiet transcript during a long reasoning step does not mark it inactive.
- The Limits report keeps, in `quota-ledger.json`, each limit's latest reading and last split rise, the use read since then (times, token counts, model names, project folders, and session ids), and points per day and project for 90 days. Use a limit can no longer split is dropped; an account with no limit read yet keeps its use for at most eight days, waiting for a first reading. The first run reads the times of the last eight days of use once, so the current windows can be split from their start.
- The Activity report keeps spans of work and waiting, with their times, states, project folders, session ids, and, for an approval, the tool name, in `activity.json`, for 30 days.
- A branched or forked Claude session copies earlier replies into its own log. `usage-replies.json` remembers, by hash, which log counted each reply for 40 days, so a copy is not counted again.
- Warden stores the Claude bridge status, the latest event per session, the latest value of each limit window (`usage.json`), and the usage history under `~/Library/Application Support/Warden`. The prompt socket lives in its `ipc` folder, open only to your user. Events older than two days and status files older than seven days are removed. Provider logs remain owned by their providers.
- Plan prices you enter stay in Warden's preferences. The Automations folder holds only the scripts you add; their latest runs are kept in memory. The start of an absence and the incident a status page names are kept in memory only.
- With **Check the provider's status page when a session fails** on, Warden reads `status.claude.com` or `status.openai.com`, at most every five minutes and only while a session has stopped on an error that may be the provider's. The request carries no cookies and nothing about your sessions.
- **Settings → Power → Keep the Mac awake while agents work** prevents idle sleep only while a monitored session is working. It defaults to power adapter use; optional battery use stops at 20% or less. The display may turn off and the screen may lock. The menu's **Keep Awake** item shows the current state and can toggle protection.
- **Keep working with the lid closed** uses the bundled, signed `WardenPower` service. Turn it on, then approve Warden in **System Settings → General → Login Items & Extensions** if macOS asks. It temporarily applies `pmset -a disablesleep 1`, including disabling Sleep in the Apple menu. Use a ventilated surface, not a bag. It follows the same activity and battery rules, and leaves an already-disabled system setting alone. The option starts off; a preview or ad-hoc build cannot enable the service.
- Warden renews closed-lid requests every five seconds. The service independently checks power, the 20% battery floor and critical thermal pressure, restores sleep when the connection closes or a request expires after 25 seconds (checked every five seconds), and recovers an interrupted change on its next launch, including after reboot. A scan older than one minute also pauses protection. **Remove Power Service** restores sleep before unregistering it. This uses Apple's [Service Management API](https://developer.apple.com/documentation/servicemanagement/smappservice), with signed XPC peers and a root-owned restore marker; no password is read or stored by Warden. Actual closed-lid behavior still needs verification on the Mac and macOS version being used.
- While answering is on, Warden stays connected to each Codex account's shared app-server through its local socket, and asks it only which threads are loaded, a waiting thread's status and folder, and, while a thread waits, its current turn, for the files an edit would change. Commands, paths, and questions stay in memory.
- In remote mode, `Phone/remote-devices.json` holds private device credentials with owner-only permissions. The phone stores its credential locally; prompt content stays in memory. The relay stores routing-token hashes, last-connection times and push subscriptions, with no session history.
- In local phone mode, `Phone/certificate.json` holds Warden's server certificate with its key and the root the phone installs, and `Phone/devices.json` the paired phones with a hash of each one's secret, both readable only by your user. What a phone shows is sent to it when it asks, encrypted, and never written to disk.
- `Widget/snapshot.json` holds what the widget shows: folder names, agents, states, tool names, and limits.
- With train-guard installed, opening the menu reads its `ignored-agents` lists and its running guards: the JSON records in `~/.train-guard/run` for the Python package, or the records and the end of the logs in `~/.claude/tools/train-guard` for the earlier shell script. A package guard counts as running only while a process with its recorded id and start time exists, and a shell guard while its recorded process still runs the script's supervisor for that job. Checking a session under **Ignore train-guard** writes the session id, agent, and folder name to `ignored-agents`. Warden never pauses, resumes, or starts a job itself.
- Limit percentages and reset times come only from provider telemetry. A sudden drop in used percentage is reported as an **observed change**, not a promised reset.
- `~/Library/Application Support/Warden` can be deleted to remove Warden's data. The Claude settings backups are kept in `~/.claude/` for recovery.
